# Developing the autonomous software

Where the algorithms go, how `ros2_ws` works, and the typical workflow from an idea to a test in CARLA.
Setup must be done first ([main README → Setup](README.md#1-setup-once)).

---

## 1. The big picture

```
 simulator (WebDriveSim or CARLA)                     our code (container "acc")
 ─────────────────────────────────                    ──────────────────────────────────────────
 /carla/ego_vehicle/odometry   ─┐                     acc_node.py   (ROS: reads topics, 20 Hz)
 /carla/ego_vehicle/waypoints  ─┼──── ROS 2 topics ──►    │
 /carla/ego_vehicle/objects    ─┘                         ├─► acc.py           speed / distance
                                                          └─► lane_keeping.py  steering
 /carla/ego_vehicle/vehicle_control_cmd  ◄────────────  throttle, brake, steer
```

Both simulators publish **the same topics**, so the same code runs on both, unchanged.
Full topic list: [WebDriveSim guide → Main topics](docs/WEBDRIVESIM.md#main-topics).

---

## 2. The `ros2_ws` folder

```
ros2_ws/
├── src/                          ← YOUR CODE. Only this folder is edited
│   ├── acc_lane_keeping/         package: our driving algorithms
│   │   ├── acc_lane_keeping/
│   │   │   ├── acc_node.py       the ROS node: subscribes, calls the algorithms, publishes
│   │   │   ├── acc.py            ACC algorithm (pure math, no ROS)
│   │   │   └── lane_keeping.py   lane keeping algorithm (pure math, no ROS)
│   │   ├── setup.py              list of executables (entry_points)
│   │   └── package.xml           dependencies (message packages)
│   └── bringup/                  package: how things are started
│       ├── launch/               acc.launch.py, webdrivesim.launch.py, carla.launch.py
│       ├── config/params.yaml    tuning values of our nodes
│       └── bringup/carla_adapter.py   fills in for CARLA what WebDriveSim has (lane info)
├── build/  install/  log/        ← generated by ./scripts/build.sh. Never edit; safe to delete
```

- The `acav` folder is **shared live** with the containers: save a file on your PC and the container sees it.
- Our code is compiled with `--symlink-install`, so changes to existing `.py` files need **no rebuild**,
  only `./scripts/restart.sh acc`.
- You never need ROS on your PC: building and running happen in Docker via the scripts.

## 3. Where the algorithms go

**Rule: keep the math separate from ROS.**

| File type | Contains | Example |
|---|---|---|
| **algorithm** (`.py`, no ROS import) | functions: numbers in → numbers out | `acc_acceleration(v, v_set, gap, v_lead, p)` in `acc.py` |
| **node** (`*_node.py`) | subscriptions, timer, conversion of messages, publishing | `acc_node.py` |
| **parameters** (`params.yaml`) | every tuning value | `v_set`, `time_gap`, `lookahead_gain` |

Why: the algorithm files can be read, tested and reused without ROS or a simulator,
and the node stays a short "glue" file.

### Pick your case

| You want to… | Put it in | Then run |
|---|---|---|
| **tune** the existing behaviour | `ros2_ws/src/bringup/config/params.yaml` | `./scripts/restart.sh acc` |
| **improve** ACC or lane keeping | `acc.py` / `lane_keeping.py` | `./scripts/restart.sh acc` |
| **add an algorithm** used by the same node (e.g. a new lateral controller) | a new file in `acc_lane_keeping/acc_lane_keeping/`, imported in `acc_node.py` | `./scripts/build.sh code`, `./scripts/restart.sh acc` |
| **add a new node** (e.g. lane change, perception) | see [4. Add a new node](#4-add-a-new-node) | build + start with its container |

New tuning value? Add it to `DEFAULTS` in the node **and** to `params.yaml` under the node's name (`acc_node:`).

## 4. Add a new node

Example: a `lane_change` node in the same package.

**Step 1 — Algorithm file** `ros2_ws/src/acc_lane_keeping/acc_lane_keeping/lane_change.py` (pure math, no ROS).

**Step 2 — Node file** `ros2_ws/src/acc_lane_keeping/acc_lane_keeping/lane_change_node.py`
(copy `acc_node.py` as a template: rename the class and the node name, keep `main()`).

**Step 3 — Register the executable** in `ros2_ws/src/acc_lane_keeping/setup.py`:
```python
entry_points={'console_scripts': [
    'acc_node = acc_lane_keeping.acc_node:main',
    'lane_change_node = acc_lane_keeping.lane_change_node:main',
]},
```
New message types? Add an `<exec_depend>` line for their package in `package.xml`.

**Step 4 — Parameters** in `ros2_ws/src/bringup/config/params.yaml`:
```yaml
lane_change_node:
  ros__parameters:
    my_value: 1.0
```

**Step 5 — Launch file** `ros2_ws/src/bringup/launch/lane_change.launch.py` (copy of `acc.launch.py`):
```python
return LaunchDescription([Node(package='acc_lane_keeping', executable='lane_change_node',
                               parameters=params, output='screen')])
```

**Step 6 — Container** in `docker/compose.yml`, next to `acc`:
```yaml
  lane_change:
    <<: *common
    command: ros2 launch bringup lane_change.launch.py
```

**Step 7 — Build and run:**
```bash
./scripts/build.sh code
./scripts/start.sh webdrivesim lane_change
./scripts/restart.sh lane_change        # after each change
```

> Two nodes must not publish `vehicle_control_cmd` at the same time: they would fight over the car.
> Either one node decides the final command, or the new node publishes its own topic that `acc_node` reads.

## 5. Are the tests necessary?

**No, they are optional.** Nothing runs them automatically and the simulators work without them.
They are useful as a **quick check** before opening a simulator.

| File | What it is | When it's worth it |
|---|---|---|
| [`tests/closed_loop_test.py`](tests/closed_loop_test.py) | runs the **real** `acc_node` without ROS or a simulator: a car follows a slower one on a straight road. Prints `OK` or `CHECK THE RESULT`. A few seconds, any PC with Python 3 | after changing `acc.py`, `lane_keeping.py` or `acc_node.py`: catches crashes and gross errors in seconds |
| [`tests/carla_traffic.py`](tests/carla_traffic.py) | **not a test**: a helper that sets up an overtaking scenario in CARLA (slow car ahead, optional oncoming car) | when you validate in CARLA with traffic |

```bash
python3 tests/closed_loop_test.py ros2_ws/src
```

Limits: `closed_loop_test.py` covers only the ACC + lane keeping node in one scenario, and it replaces ROS
with small stand-ins. If you add subscriptions with **new message types** to `acc_node.py`, add stand-ins
for them at the top of the test, or it will fail on import. New nodes have no test: write one only if it
saves you time (same idea: call the algorithm functions with numbers and check the result).

The real test is the simulator: **WebDriveSim scenarios** for daily checks, **CARLA** for validation.

## 6. Typical workflow

**Step 1 — Design** the algorithm on paper: inputs (which topics), outputs, parameters.

**Step 2 — Write the algorithm** as pure functions in a new or existing file (section 3).

**Step 3 — Wire it into the node**: read the inputs from the messages, call your functions, publish.
Put the tuning values in `params.yaml`.

**Step 4 — Quick check without a simulator** (optional, seconds):
```bash
python3 tests/closed_loop_test.py ros2_ws/src
```

**Step 5 — Run in WebDriveSim:**
```bash
./scripts/start.sh webdrivesim          # open http://localhost:8080
```

**Step 6 — Iterate**: edit → restart → watch. Repeat.
```bash
./scripts/restart.sh acc                # shows the log; Ctrl+C stops watching
```

**Step 7 — Test with scenarios**: build the situation you need (traffic, curves, slow car, overtaking)
in the page and save it in `maps/webdrivesim/` ([guide](docs/WEBDRIVESIM.md#create-your-own-map-and-scenario)).
Load it with `WEBDRIVESIM_WORLD` for repeatable runs (`WEBDRIVESIM_SYNC=true` makes them identical).

**Step 8 — Validate in CARLA** (realistic physics):
```bash
./scripts/stop.sh
./scripts/carla.sh                      # terminal 1
./scripts/start.sh carla                # terminal 2
```
With traffic: in `./scripts/shell.sh` run `python3 ~/acav/tests/carla_traffic.py` ([options at its top](tests/carla_traffic.py)).

**Step 9 — End:**
```bash
./scripts/stop.sh                       # + Ctrl+C in CARLA's terminal
```

## 7. Look inside while it runs

Open a terminal with ROS: `./scripts/shell.sh`, then:

| Goal | Command |
|---|---|
| list the topics | `ros2 topic list` |
| see a topic's messages | `ros2 topic echo /carla/ego_vehicle/vehicle_control_cmd` |
| check the rate | `ros2 topic hz /carla/ego_vehicle/odometry` |
| list running nodes | `ros2 node list` |
| change a parameter live | `ros2 param set /acc_node v_set 20.0` (lost at restart: also edit `params.yaml`) |
| plot values over time (speed, gap, steer …) | `ros2 run plotjuggler plotjuggler` → *Streaming: ROS 2 Topic Subscriber* → drag a field onto the plot |
| 3D view (car, radar/lidar points, camera) | `rviz2` (Fixed Frame: `map`), or add `foxglove` to `start.sh` |
| record a run to replay later | `ros2 bag record -s mcap -a` (Ctrl+C to stop); open the file in PlotJuggler or Foxglove |
| a node's log | `docker compose -f docker/compose.yml logs -f acc` (from the `acav` folder) |

Print from your node with `self.get_logger().info(f'gap={gap:.1f}')`: it shows up in the log.

## 8. Sensors

**WebDriveSim:** the sensors are set in the page, step *2 Sensors* (position, range, noise), and saved with the world.

**CARLA:** our car and its sensors are listed in a JSON file. Editing it is enough, no build:

| File | Used when |
|---|---|
| [`config/carla_ego_light.json`](ros2_ws/src/bringup/config/carla_ego_light.json) | `CARLA_CAMERAS=false` (default): GNSS, IMU, collision, lane invasion, ground truth |
| [`config/carla_ego.json`](ros2_ws/src/bringup/config/carla_ego.json) | `CARLA_CAMERAS=true`: the same + cameras `rgb_front`, `rgb_view` and `radar_front` |

One sensor = one line: `type` (CARLA sensor), `id` (its topic becomes `/carla/ego_vehicle/<id>`), the CARLA
attributes (range, noise, image size …) and `spawn_point` (position on the car: x forward, y left, z up, in m).
Example, a radar in the light file:
```json
{"type": "sensor.other.radar", "id": "radar_front", "horizontal_fov": 30.0, "vertical_fov": 10.0, "range": 150.0,
 "spawn_point": {"x": 2.3, "y": 0.0, "z": 0.7, "roll": 0.0, "pitch": 0.0, "yaw": 0.0}},
```
Apply: `./scripts/restart.sh carla_bridge` (it removes the old car and spawns the new one).
Check: `ros2 topic list | grep ego_vehicle`, then plot it as in [7](#7-look-inside-while-it-runs).
The `sensor.pseudo.*` lines are ground truth (exact odometry, objects): our code uses those.
